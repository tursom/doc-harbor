# 扫描性能与一致性

记录日期：2026-11-08。本文描述当前实现和本地验证，不表示服务已部署。

## 扫描流程

1. 同步镜像并固定本轮分支提交，读取当前扫描规则和已有索引。
2. Git 枚举、最近提交查询、正文读取和历史读取全部在 SQLite 写事务之外完成。
3. 用分支事务原子提交准备好的索引、删除标记、历史事件、最新视图及成功检查点；提交前再次检查配置，分支提交后取消也不会留下目录与版本路径混合的状态。
4. 根据本轮完整分支列表更新最新视图的参与资格；最终发布事务再次检查配置。

SQLite 写连接仍为一个；页面查询使用独立只读连接池及 WAL，只能读到已提交的数据。没有新增数据库服务、任务队列表或功能开关。进程内最多执行一个扫描，繁忙的新请求返回 409。

## 增量条件

`repo_refs.scan_config_hash` 保存扫描规则指纹，覆盖路径、包含/排除规则、文件大小及分支选择规则。旧记录没有指纹时先完整检查一次。

- 上次完整成功、规则相同、HEAD 相同：跳过文件和历史处理。
- 上次完整成功、规则相同、旧提交是新提交祖先：按内容和真实最近提交比较，只更新改变的文件；历史范围为旧 HEAD 到新 HEAD。
- 首次扫描、规则变化、失败重试、旧提交对象缺失或非连续历史：完整检查当前范围。
- `force=true` 显式完整重建，不扩大文档范围。

失败分支不推进成功检查点。已完成的分支可以保留检查点，中断后重试不会把未完成分支误判为成功。

## Git 批量读取

线性历史通过一次日志读取计算多个路径的最近提交。合并历史不能直接按多文件日志第一次出现取值：它与 Git 单路径的历史简化不同。合并算法读取完整 DAG，批量比较父树，并逐路径选择第一个 TREESAME 父节点；非空批次使用两个 Git 进程，对照真实 `git log -1 -- path` 验证。

Markdown 正文使用 `git cat-file --batch`，每批最多 64 个对象及约 8MiB 正文，仅缓存标题。单个超大但配置允许的对象仍需独立读取。对象和路径协议使用 NUL 或对象长度界定，取消和超时负责回收进程。

## 一致性边界

- 复制文件建立独立身份，只有重命名继承当前分支的源身份。
- 重命名目标处理失败时保护旧源版本；失败文件保留旧 blob 和旧 HEAD。
- 净 diff 只匹配身份，重命名事件的提交归属来自真实历史，避免把后续内容修改伪造成重命名。
- 历史事件重新归属先去掉完全等价的副本，再移动剩余事件，允许重复回填。
- 被远端删除或取消跟踪的分支保留历史索引，但退出智能最新候选。
- 全部分支无变化且上轮成功时，不重写智能最新索引；上轮发布失败或候选资格变化时仍重建。

分支的短事务不是整个仓库扫描的单个事务：部分成功仍按已提交文件数统计。有变化时智能最新视图仍统一重算，这是当前剩余的主要 SQL 成本；读取通过独立连接继续提供服务。

## 验证

真实临时 Git 仓库与 SQLite 回归覆盖：普通刷新、完整重建、单文件修改、内容还原、删除、重命名、复制、强推、规则变化、失败重试、取消和重启恢复；Git 合并算法额外覆盖多父提交、冲突解决、模式变化、特殊路径和随机 DAG。文件 WAL 的连接隔离通过保持写事务期间读取接口可用验证。

本地 HTTP 样本使用 12,300 个文件、两个分支和合并历史：首次写入 24,600 个分支文件版本约 7.7 秒；无变化刷新观察到约 0.1 秒；单文件更新只处理 1 个文件，约 2.6 秒。扫描期间 151 次读取全部成功，最慢约 4.9 毫秒。该样本用于验证工作量、生命周期和读取隔离，不作为其他仓库的耗时承诺。

浏览器通过真实本地服务验证：写入索引阶段显示分支和准备文件数，正文持续可读，取消后仍保留阅读状态；另有离线交互回归覆盖轮询、切换仓库和页面重新打开。
